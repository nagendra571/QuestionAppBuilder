# Integrating QuestionAppBuilder

For an agent-facing guide to configuring applications from business requirements, see `docs/AGENT-APPLICATION-BUILDING-GUIDE.md`. It covers the feature model, authoring workflow, constraints, examples, verification, and a reusable agent prompt. This integration document covers consuming-host responsibilities.

QuestionAppBuilder is an ASP.NET Core MVC/Razor Class Library platform. A consuming host owns SQL Server, authentication, authorization policies, branding/layout, email delivery, HTTPS origin, and data-protection keys. The libraries own questionnaire definitions, immutable publication, response persistence, visibility, validation, scoring, and reporting.

## Packages and framework

The released libraries target `net8.0` and EF Core 8. The sample host and package-consumer acceptance host use the ASP.NET Core MVC stack. The standalone package acceptance script also builds a .NET 10 host from packages. That proves this package set can be consumed by the tested .NET 10 SDK/runtime; it does not mean the libraries multi-target `net10.0`.

Install matching versions of `QuestionAppBuilder.Infrastructure`, `QuestionAppBuilder.Core`, `QuestionAppBuilder.Editor`, and optionally `QuestionAppBuilder.Reports`. Package dependencies supply Domain and Application transitively. Register one Infrastructure database connection, the runtime and editor surfaces, and Reports only when analysts should have that surface. Configure a host-authentication adapter, explicit fill/design/report policies, and an email sender for email-link applications. See the sample host README for a complete development composition.

The default route prefixes are `/App`, `/ConfigureApp`, and `/Reports`; every prefix is configurable. Register host authentication before authorization, call `UseRateLimiter()` for the configured IP limiter, then map the selected platform surfaces. Use the host's MVC layout and scoped CSS; do not expose a privileged surface without its named policy. Reports enforce their policy on both area and conventional routes.

## Respondent identity and access

For host-sign-in applications, map the authenticated host's validated issuer and stable subject to respondent ownership. Never use an unvalidated display name or email as the durable identity key. For email-link access, configure a trusted HTTPS public origin and a sender. Access links contain one-time random tokens; only their digest is stored. Unknown, expired, consumed, and wrong-owner links fail closed. Cookies and antiforgery require HTTPS. Hosts should configure their external proxy/forwarded-header trust explicitly.

## Package verification

`scripts/Test-Packages.ps1 -FeedPath <empty-absolute-directory> -Version <unique-prerelease>` creates six packages, restores a host that has only PackageReferences to them from an isolated feed/cache, and checks compiled Editor/Reports views and Core/Editor/Reports assets under custom prefixes. It then runs the real-browser package consumer test. It does not publish packages. `scripts/Test-Release.ps1` adds SQL Server and full solution acceptance.

## Authoring performance

The built-in draft workspace loads its definition once and calculates readiness from that same snapshot through `IDraftService.GetWorkspaceAsync`. The default interface implementation preserves compatibility for existing custom services; override it to provide the same single-load behavior in a custom implementation.

Draft and application-repository graph loaders use scoped split queries rather than joining all options, rules, and visibility collections into one result. On relational databases, a short Serializable transaction protects graph materialization when no caller transaction exists. Existing Save/Publish transactions and revision/rowversion conflict checks remain in place. These changes require no schema migration or cached definition data. See Microsoft's guidance on split-query performance and consistency: https://learn.microsoft.com/en-us/ef/core/querying/single-split-queries.

### Guided total-limit recipe

The composition editor's Limit a combined total recipe stages an ordinary Sum calculation and a Validation rule with a LessThanOrEqual check. Both are persisted by the existing Composition.Save request with its expectedRevision, authorization, antiforgery and full-definition validation. The recipe adds no route, public service signature, schema, evaluator semantics or persisted recipe metadata. Published definitions and historical submissions are unchanged.

Recipe state is separate from advanced configuration until the author reviews and adds the pair. Unadded recipe edits protect navigation and must be added or discarded before Save configuration. Source-category ordering follows the evaluator's SortOrder/Id order, and the maximum is checked for exact decimal preservation through the browser's JSON numeric representation. Unsupported precision is rejected. Existing missing/hidden input and target-applicability semantics remain in force.

### Draft configuration search

Workspace search reads one saved graph through IDraftService.GetAsync and searches authored text and resolved direct reference names in memory. It does not issue per-result queries, evaluate answers, create a persistent index, or require a schema change. The additive GET endpoint under the configured editor prefix, Drafts/{applicationId}/Search, requires the design policy and a matching expectedRevision; responses are no-store and stale revisions return409. Existing controller/service signatures remain unchanged.

The workspace flushes autosave before searching, discards stale responses, and uses allowlisted workspace/composition destinations. Composition retains explicit saving. Search is scoped to the application's current draft; it excludes responses, submissions and published history. A malformed configuration warning indicates incomplete coverage. Existing published versions and frozen submitted results are unaffected.

### Designer preview visibility explanations

The existing authorized preview endpoint returns additive `HiddenItems` and `Revision` fields. A nullable `EvaluationResult.HiddenElementReasons` property records the actual short-circuited visibility decision without changing its positional constructor or `IDefinitionEvaluator`. The default evaluator also records content hidden by resolved dynamic labels. This is diagnostic metadata; condition-visible element IDs keep their existing meaning, and dynamic hiding remains a separate presentation decision.

Preview maps trace IDs to configured names and settings links. `null` trace data from a custom evaluator means explanations are unavailable. These reports are not added to respondent rendering models or persisted submission snapshots. The editor sends optional `PreviewRequest.ExpectedRevision` after flushing autosave; mismatches return 409. Existing callers that omit the revision remain supported. The UI invalidates explanations when draft configuration or preview answers change and discards superseded responses. No database migration is required.
### Shared preview scenarios

Reusable preview scenarios are application-owned authoring data in the new PreviewScenarios table, separate from version definitions and response/submission storage. Apply the generated PreviewScenarios EF Core migration through the host's normal deployment process before using this feature. The migration creates a new table, application foreign key, concurrency rowversion and `(ApplicationId, Name)` index for scoped listing/counts; it does not backfill or reinterpret published definitions or submissions. Migration rollback deletes saved scenarios, so preserve them before rollback. The generated SQL creates only the empty table/index, FK and migration-history entry in a transaction; no existing-row backfill or index rebuild is required. Schema locks still apply during DDL. No migration is applied to an existing host by this implementation task.

New IPreviewScenarioService/IPreviewScenarioRepository contracts and an authorized, antiforgery-protected scenario controller are additive. Schema1 JSON stores element/option logical keys, saved answer types and invariant numeric strings. Load/run resolves those keys against the requested current draft version/revision. Runs use the configured IDefinitionEvaluator with requireComplete:true and one snapshot for a run-all request; definition errors and incompatible references are reported as NeedsRepair rather than passing expected-invalid assertions. Scenario writes atomically verify the current draft and scenario revision, independently from the draft nonce; they do not modify the definition. Designer reads use untracked queries. Scenarios survive draft cloning because logical keys survive, and application deletion cascades its scenario rows.

Limits are 50 cases per application, 500 answer entries per case and 256 KiB UTF-8 payloads. At least one explicit expected validity/total is required. No upload tokens/file data, response creation, publication, automatic expectation acceptance, or clock pinning is supported. The editor flushes draft autosave and discards superseded results; loading explicitly replaces preview inputs. Existing public constructors and service signatures retain their shape.
### Designer preview scoring explanations

The default scoring engine adds nullable, transient `SubmissionScore.Diagnostics` without changing its positional constructor or `IScoringEngine`. Question diagnostics capture actual award eligibility and contribution, per-unit inputs/rate/cap, and FirstMatch winners. Combined diagnostics originate from the composition pass that supplied the score, including visited conditions/checks and band winners; preview does not substitute the evaluator's separate composition pass or rerun rules to explain them. A custom scorer omitting diagnostics remains supported and yields an unavailable explanation. An unsupported total-score configuration reports unavailable diagnostics explicitly; invalid combined configuration does not erase valid question awards.

The authorized draft preview adds nullable `PreviewResponse.Scoring`, mapping diagnostics to named, text-only explanations with existing question-rule and combined-rule edit links. Decimal input values use invariant strings to avoid JavaScript Number rounding. The existing revision/request protections invalidate these reports on draft or answer edits. `SubmissionScore.Diagnostics` and `CompositionResult.CombinedScoreRules` are excluded with `System.Text.Json.Serialization.JsonIgnore`; existing persisted question rule traces, composition awards, frozen submissions and respondent render models retain their formats and semantics. Deploy matching packages and assets to load the new preview UI; no migration, data backfill or republishing is needed.
### Designer preview combined-validation explanations

The authorized preview response adds nullable `FailedValidationRules`, mapped from a transient evaluation trace keyed by rule ID. Checks record their actual used values and outcomes during the existing short-circuited evaluation; calculated-value input effects are propagated from the existing calculation pass. No additional rule evaluation or respondent query is performed. Invariant `LeftValueText`/`RightValueText` display fields preserve decimal precision beyond JavaScript Number; the inspector uses these strings for actual values. Missing/hidden numeric inputs still read as zero, selected options as one/zero, and unavailable calculation operands still fail comparisons.

`CompositionResult.FailedValidationRules` is marked `System.Text.Json.Serialization.JsonIgnore`, so submission snapshot JSON does not gain diagnostics. `EvaluationResult` exposes an additive nullable trace property for the preview mapper; existing constructors and evaluator signatures remain. A custom evaluator without the trace, or configuration errors that prevent a dependable report, returns unavailable rather than a success claim. The UI shares the existing revision and stale-result checks for all preview explanations.

Rule edit links support the additive `#Rules/{guid}` fragment in composition. Existing pane fragments remain supported; matching rules open and receive focus without saving or changing persisted configuration. Diagnostics identify the actual message target and configured live-feedback setting; the preview field still shows only its first error. No schema migration or historical snapshot reevaluation is involved.
## Document answers

`AnswerType.UploadDocument` accepts one PDF, Word `.docx` (without VBA), or UTF-8 `.txt` file per question, up to 10 MiB. Required validation, Presence scoring, visibility rules, and option-linked follow-ups work as for other answers. Designer preview simulates a file without storing bytes.

Apply the UploadDocuments EF migration before serving this type. The default `IResponseDocumentService` stores file bytes separately in SQL Server's ResponseDocuments table; normal answer queries load only filenames. Include these tables in database backup/retention policies. Runtime requires JavaScript for upload/remove and uses antiforgery-protected multipart requests. Allow multipart bodies of at least 11 MiB in any reverse proxy or host request-size configuration. Ordinary answer saves cannot set or clear document answers.

Downloads enforce response ownership/email-grant scope, or the configured Reports policy for an applicable submitted answer. Files download as attachments with no-store and nosniff headers. Files from hidden branches are retained while editing and deleted atomically on submission. A submitted response cannot replace or delete its submitted files. CSV exports contain filenames. Extension/content format checks are not malware scanning; a host that requires scanning should provide its own `IResponseDocumentService` implementation. Never expose document bytes through public static-file paths.

## Points-per-unit question scoring

Numeric range scoring rules on Number questions can choose Award method: Fixed points or Points per unit. Fixed (enum value 0) preserves existing behavior. Points per unit uses the integer PointsPerUnit rate and optional integer MaximumPoints cap; the existing Points field remains the fixed award. The question must require whole numbers, have a nonnegative minimum, and have either a maximum answer or a score cap. Rates and caps are nonnegative, and the maximum rule award is 1,000,000. Definition validation checks the total possible award including combined-rule points before publishing.

Rule eligibility is checked before calculating answer multiplied by rate. A configured cap applies to that rule before Additive or First Match aggregation. Blank, hidden, invalid negative/fractional, or out-of-range answers do not receive a per-unit award. There is no implicit rounding. A score cap limits awarded points; it does not replace question answer validation. Preview, rule traces, submitted question/category totals, and reporting use the actual computed award. New settings are copied through draft/version/category/question duplication; published definitions and submitted scores remain immutable.

Apply migration `20261022153143_PointsPerUnitScoring` before using this feature. It adds AwardMethod (Fixed by default), PointsPerUnit (0 by default), and nullable MaximumPoints to ScoringRules. Per-unit definitions use scoring engine version 2.1; existing fixed-only/composition engine markers are preserved. The original AddRuleAsync service signature is retained; AddRuleWithAwardMethodAsync provides the extended authoring operation.

## Generic composition (optional per published version)

### Dates, reusable values, and dynamic text

Date questions store an invariant `yyyy-MM-dd` answer in the existing TextValue field. They are separate from free-text questions: formatting does not change the stored date or turn arbitrary text into a date. Date questions support required-answer validation and Presence scoring; numeric range scoring continues to require Number questions.

Optional `CompositionDefinition.DynamicText` configuration adds reusable typed values and structured text templates. Sources include question answers, existing calculated fields, other reusable values, constants, and Today. Supported operations include joining text with a separator, formatting dates, calculating age in completed years, and decimal addition, subtraction, multiplication, and division. References use stable logical identifiers instead of question labels, so renaming a question does not break its references. These values are for displayed text; they do not extend scoring or visibility rules.

Templates can customize content/question labels, help text, a review summary, and submission confirmation. Literal text and inserted values are stored separately; neither designer text nor respondent answers execute code. Rendered values are HTML-encoded, and text inside an answer is never interpreted as another template. Missing, hidden, and invalid inputs remain unavailable rather than silently becoming zero. Templates can provide fallback text; content can be hidden until its values are available. Selected choices use the published option labels in definition order, and document answers expose filenames only.

The versioned timezone defaults to UTC and determines Today from one captured evaluation instant. Age uses completed calendar years, rejects future birth dates, and treats a February 29 anniversary as February 28 in a non-leap year. Division by zero is unavailable. Publication validates references, operand types, cycles, and supported configuration limits. Forward references in displayed text are allowed and remain unavailable until answered.

The submission composition snapshot also stores the evaluation instant, timezone/reference date, typed values, resolved text, and (for new submissions) visible category and element identifiers. The renderer uses the evaluated element set for ordinary content and questions; a missing element set in a custom/legacy evaluation retains the previous question-only filter and shows content in visible categories. The evaluator fix has no version gate or schema change, so it applies to new evaluations of existing published and pinned in-progress definitions after deployment. Reopened submitted applications use the frozen result, so visibility and dynamic text do not change when viewed later. Older submissions without visible-element IDs retain their prior content behavior; when no visible-category snapshot exists, reopening includes unconditional categories and categories with applicable saved question states. Conditional content-only categories without a category snapshot are omitted because their visibility cannot be established safely without reevaluation.

### Groups, calculations, and combined rules

Validation rules optionally enable "Show validation while answering" (`ShowWhileAnswering`, default false). This versioned JSON flag requires no additional migration. Opted-in failures appear for the current category after the existing background autosave (600 ms typing pause plus server response), and clear after valid answers save. JavaScript and a successful request are required for live updates. All rules retain normal sequential forward-navigation and submission enforcement regardless of the flag. Backward/free navigation behavior is unchanged. Live feedback does not expose unrelated required-field errors. Publish an updated draft and start a new response to use changed settings; existing responses retain their pinned version.

Applications may add a generic composition configuration to a draft; applications without one continue to use the standard questionnaire behavior. Open **Groups, rules & dynamic text** from the authoring workspace at `/ConfigureApp/Composition/Index/{id}` (the editor route prefix can be customized). The builder groups existing questions as presentation metadata; grouped questions remain ordinary questions with their usual answer, visibility, validation, and scoring behavior. Both pages share Questionnaire/Groups area navigation and retain a route back to application details.

The questionnaire workspace autosaves edits and waits for pending saves before following ordinary primary-clicks on same-origin, current-tab links within its authoring surface. Modified clicks, downloads, external links, and new-tab links retain their native behavior. A save conflict keeps the workspace open and the edited values available for reconciliation; transient network failures can be retried. The composition builder retains an explicit **Save configuration** action; incomplete configurations may be rejected, so it does not autosave. Unsaved composition changes trigger the browser's leave-page warning.

The workspace exposes a lazy **Used by and related items** disclosure for each question or content element. Opening it flushes pending workspace edits, then calls the revision-pinned, authorized `GET /ConfigureApp/Drafts/{applicationId}/Dependencies?elementId={logicalKey}&expectedRevision={base64Revision}` endpoint against one saved draft snapshot (the editor base path is configurable). The response is never cached; a mismatched revision returns 409 and an element outside the application draft returns 404. The application analyzer lists direct and transitive configured references (visibility, groups, calculations, combined rules, dynamic variables/templates), ownership, follow-up relationships, and potential first-visible targets. It does not evaluate respondent visibility or predict deletion effects. No database schema or draft-service interface change is required. Links are generated from editor routes and allowlisted composition sections.
Draft deletion from application details uses an additive `IDraftDeletionCoordinator`, registered by `AddQuestionAppBuilder`. The editor's authorized `Deletions/Preview` GET shows effects for a category, element, or option without saving. Its anti-forgery-protected `Deletions/Confirm` POST accepts a Data Protection token binding application, version, target identity, and revision. The coordinator reloads an existing draft, recomputes impact, rejects blockers or incomplete inspection, and applies deletion plus revision rotation in one transaction. SQL Server rowversion detects concurrent changes; a publication race rolls back all deletion writes and never clones a published version. Repair links point to the existing authoring sections; retained broken references still require correction before publication. Existing removal service signatures/routes remain compatible, and no schema migration is introduced. Hosts should deploy matching Application/Infrastructure/Editor packages for the new coordinator; existing Data Protection configuration is reused.

Calculated fields support `Sum` and `Percentage` over numeric question values, selected-option indicators, constants, and other calculated fields. Blank numeric answers and hidden source questions contribute zero. A percentage with a zero denominator has no value and is shown as unavailable. A question can optionally require whole-number input; this is an additional constraint on Number answers and defaults off.

Combined rules support validation and scoring. Conditions gate a rule and all conditions must match; checks can require all checks or any check. An option-selection source evaluates to 1 when selected and 0 otherwise. Score rules can share an ordered band group so only the first matching rule in that group contributes. Validation rules must be attached to the same or a later category than every answer they depend on; invalid future-category dependencies are rejected during configuration and definition validation.

Composition configuration is stored as JSON in `ApplicationVersion.CompositionJson`, so it is versioned with the definition and follows its immutable publication. On submission, calculated values and composition awards are serialized into `Submission.CompositionSnapshotJson`. Reports and CSV export read that stored snapshot; they do not recalculate composition against current definitions or answers. The `20261022021845_GenericComposition` migration adds these two nullable JSON columns and `Questions.WholeNumbersOnly` (default false). Apply the migration before using the new authoring or reporting fields.

`ResultVisibility` controls the immediate receipt, with `ConfirmationAndAnswerReview` adding a total and stacked read-only application review. The independent `SubmittedApplicationVisibility` setting controls scores when a respondent later opens the linked submitted application: `WithoutScores` hides all score details; `WithScores` displays the stored total and positive earned-point details. Both screens use the pinned version, saved answers, frozen category/element visibility, and the existing owner-protected document endpoint; neither reevaluates a response. The `20261024155005_SubmittedApplicationVisibility` migration adds the separate versioned setting. Older compositions without visible-category IDs omit conditional content-only categories from reopened views; snapshots without visible-element IDs preserve historical content rendering.
